# Security Policy

## Current status and supported versions

`Astraive/glint-library` is at its **foundation stage**. It contains policy files, scripts, and CI configuration only. **No themes, registry, or release artifact has been published.**

| Target | Supported | Notes |
| --- | --- | --- |
| Library releases and registry snapshots | None yet | Nothing has been released. |
| `main` (policies, scripts, workflows) | Active baseline | Repository tooling and configuration only. |

## Reporting a vulnerability (private route only)

**Do not open a public issue, pull request, or discussion** for an undisclosed vulnerability, a malicious or hostile theme or `.glint` package, a path-traversal or archive-escape proof of concept, an exfiltrating or obfuscated theme, a workflow or supply-chain compromise, or a registry-integrity flaw.

1. **GitHub Private Vulnerability Reporting (preferred):** submit a draft advisory at [Astraive/glint-library Security Advisories](https://github.com/Astraive/glint-library/security/advisories/new).
2. **Fallback:** if that is unavailable, contact maintainer `@NeerajCodz` (`https://github.com/NeerajCodz`) privately before posting details publicly.

Include the affected theme ID and version or commit SHA, minimized reproduction steps using a synthetic, rights-cleared fixture, the expected versus observed behavior, and the environment. Never attach personal files, proprietary assets, tokens, or unredacted local paths.

## Response and takedown policy

- Maintainer `@NeerajCodz` triages reports and coordinates remediation.
- Themes found to be malicious, infringing, or misleading are removed from the registry index and affected versions are advertised. Installed local packages keep working offline unless users revoke them.
- Destructive-data, archive-escape, permission-bypass, and supply-chain failures are release blockers and are never waived.

## Planned security rules for library content

- Themes must not contain install scripts, native binaries, or network-loaded executable code.
- Static audits will reject restricted-API use and remote script references.
- Integrity hashes in the registry index are generated by CI.
- Untrusted pull requests never receive secrets, and workflows never use `pull_request_target`.
- Registry metadata is an index, not a trust anchor: the installed package's own manifest is validated independently by Glint. GitHub stars are not a security signal.

These are design intentions from the Glint plan, not yet implemented controls.
